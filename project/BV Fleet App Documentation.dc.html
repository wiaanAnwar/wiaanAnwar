BV BAVARIAN RENT A CAR — MOBILE APP

Product & Engineering Documentation

v2 — hardened · Prototype documentation, September 2026

1. Overview

BV Fleet is the customer-facing rental app for BV Bavarian Rent A Car, a Khartoum-based vehicle hire operator. It lets individual, corporate and UN/INGO customers search a date-scoped fleet, request a hire, and track it through to return — in English or Arabic (RTL). This document covers the product's planning goals, the visual/interaction design, and how the current prototype is implemented.

2. Planning

2.1 Goals

  • Date-first search. Nothing books what isn't actually free — the calendar drives which vehicles show, with a "next free" date surfaced for the rest instead of hiding them.
  • Serve three account types from one app: walk-up individuals, corporate accounts with standing agreements, and UN/INGO agencies that need internal approval before a request reaches BV.
  • Payment flexibility matching how BV is actually paid: invoice-to-account, Bankak transfer, mobile money, or cash with a deposit at collection.
  • Trips that do something after booking — a live status timeline, direct call/WhatsApp to the assigned driver, amend and cancel with the policy shown up front.
  • Arabic parity. Full RTL layout and translated copy, not a mirrored afterthought.
  • Resilience. The app should degrade honestly — loading skeletons, an offline banner over cached data, and a WhatsApp fallback if a submission fails — rather than pretend everything always works.

2.3 Information architecture

Four tabs: Home (hero, quick search, active-hire card, services, account snapshot), Fleet (date-scoped results with category filters), Trips (Active / Upcoming / Past, each with a status timeline), Account (profile, agreement, business hours, contact, sign out). Search and vehicle detail open as full-screen sheets over the tab content rather than new tabs, keeping the four-tab structure fixed regardless of where the user is in a booking.

3. Design

3.1 Visual system

Palette: near-black (#0B0B0C / #1A1A1C) as the primary surface, warm gold (#F5B301) as the brand accent, and red (#DD2A26) for calls to action and status — a deliberately automotive, slightly premium palette rather than a generic light-mode rental app. Content sheets (search, results, detail, forms) switch to a near-white #F7F7F7/#fff surface for readability and to separate "browsing" from "brand" moments (hero, header, account, active-hire card).

Typeface: Poppins for Latin copy, Cairo for Arabic — swapped automatically with the language, both loaded from Google Fonts. Headings use tight negative letter-spacing; small labels/eyebrows use wide positive letter-spacing and uppercase — the two recurring type moves that give the hierarchy its shape.

3.3 States handled deliberately

  • Search skeletons while results "load" (simulated delay).
  • Offline banner — a persistent red strip when the network tweak is set to Offline, with cached data still shown underneath.
  • Submit failure — the review step can fail to submit, surfacing a retry and a "send over WhatsApp" fallback so a request is never silently lost.
  • Empty states for no fleet matches and no trips, each with a clear next action.
  • Blocked continue — the primary button visibly dims and explains itself when a required field is missing, instead of failing silently on submit.

3.4 Internationalisation

Every string in the app comes from a single English/Arabic dictionary; switching language flips dir to rtl, swaps the font family, and removes Latin-style letter-spacing (which reads badly on Arabic glyphs). Phone numbers, references and dates that must stay left-to-right (e.g. 0912301407) are pinned with dir="ltr" even inside an RTL page.

4. Implementation

4.1 Stack

The app is a single Design Component — one template driven by one logic class, re-rendering on every state change with no page loads and no backend. All data (fleet, trips, translation strings) is defined as in-file constants standing in for what would be live API calls in production.

4.2 Data model

EntityShapeNotes
VEHICLESid, name, category, badge, seats, bags, gear, fuel, daily rate, units[], included itemsEach vehicle has several physical units (one per licence plate), each with a busyUntil day index
trips[] (state)ref, stage (0–4), vehicle, plate, date range, location, driverStage maps to the status timeline; negative day indices represent past trips
ADDONS, PAY, APPROVERS, LOCSStatic reference listsRendered via <sc-for> into booking-step options

Availability is computed, not stored: freeUnits(vehicle) filters a vehicle's units to those whose busyUntil falls before the selected pickup date; nextFreeIdx(vehicle) finds the earliest date every unit is free, used for the "next free" label when nothing matches the current dates.

4.3 State & rendering

Component state covers auth step, active tab, search dates/location, the open detail/booking sheet, booking-form answers, and UI ephemera (toasts, cancel-sheet target). A single renderVals() method recomputes, on every render: the active translation table, every inline style string used by the template, derived labels (date ranges, cost breakdowns, VAT, deposit), and the click handlers passed to buttons. The template consumes these as named holes and <sc-if>/<sc-for> blocks — no logic lives in the markup itself.

4.4 Booking flow

A 5-step sheet, tracked as state.step:

  1. Dates & vehicle — recap of the search and the assigned plate.
  2. Driver & extras — chauffeur vs self-drive, toggled add-ons.
  3. Billing & approver — who's billed, and (for corporate/agency accounts) which named approver the request routes to.
  4. Payment — method selection and the resulting deposit requirement.
  5. Review & submit — full cost breakdown, VAT, total; submit can fail and offer a WhatsApp fallback.
  6. Done — confirmation screen with a generated reference number, worded differently for "sent to BV" vs "sent for approval."

Required fields block the primary button (and explain why) until filled; agency/business accounts add the approver step and PO/cost-centre fields that individual accounts skip.

4.6 Known limitations

  • No real backend — availability, pricing and trip status are local mock data, not live.
  • Vehicle imagery is a placeholder pattern pending real photography.
  • No BV-side dispatch app or live driver map yet — driver contact is a static number, not a live position.
  • Arabic copy has not had a native-speaker review pass before release.
